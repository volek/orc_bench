## Вывод

Пилот scale S на Spark, concurrency 1, закрывает вопрос «какой одиночный layout-фактор ускоряет типичный запрос», и не закрывает SLA 3 с как решение для масштаба L.

- Точечные запросы уже внутри SLA: `Q02` (96 строк) p50 **169 мс**, `Q03` (17 строк) p50 **398 мс**, `Q04` (`COUNT` по `name='LOGON'`) p50 **281 мс**. Это плоский перезаписанный layout без партиций, сортировки и bloom.
- SLA-гейт прогона в целом **не пройден** (`slaGateOverall=false`): 55 из 75 ячеек проходят, 20 нет. 16 провалов — `Q07_NARROW` и `Q07_WIDE`. Ещё 4 — партиция `event_date+event_hour` на `Q02`/`Q03`/`Q04`/`Q08`.
- `Q07_NARROW` возвращает **53 673 717 строк** (`userLogin`, `createdAt` при `name='LOGON'`). Тот же предикат как `COUNT` (`Q04`) укладывается в ~0.3 с. Разница ~2.5 с — это доставка результата драйверу, а не ORC skip. Ни bloom, ни сортировка этот объём не срезают.
- `Q07_WIDE` (`SELECT *` тех же 53.7 млн строк) — **57–61 с**. Колоночный pruning относительно wide даёт порядка 14×, но narrow всё равно около порога или выше него.
- Выбранный `BEST_ORC` — `PARTITIONING` / `partition_columns=[]`, mean p50 по `{Q02, Q03, Q07_NARROW}` = **1111 мс**, mean SLA = **0.9778**. Это самый быстрый плоский layout, а не победа партиционирования: список колонок пуст. Класс тай-брейка `partitioned` в `SUMMARY.txt` возникает из-за подстроки `PARTITION` в id эксперимента.
- Партиция по `event_date` полезна только запросам с фильтром по дате (`Q01_PARTITIONED` p50 117 мс, `Q06_PARTITIONED` p50 148 мс) и замедляет все остальные в 4–9 раз. Пара `event_date+event_hour` ломает прогон: нефильтрованные запросы 16–26 с при росте файла всего на 8%.
- Bloom по `userLogin`/`session` на scale S вреден: equality-запросы медленнее на 25–85%, `Q07` не ускоряется. Сортировка в пределах шума p50 (единицы–десятки миллисекунд); единственная ячейка `Q07_NARROW`, которая сама проходит 95%, — `sorting=[__time,userLogin]` (29/30, единственный промах 3011 мс на повторе 0).
- Vectorized ORC reader стоит оставить включённым: `Q07_NARROW` −18% (4015 → 3309 мс), `Q08` −32% (1006 → 686 мс). На `Q07_WIDE` эффекта нет (+1%).
- На сырой базе predicate pushdown ускоряет только `Q02` (−19%) и замедляет `Q03`/`Q05`/`Q06` (+14…+26%). Эти абсолютные времена (0.6–0.9 с) всё равно в 3–4 раза хуже тех же запросов на перезаписанных плоских layout (~0.17–0.4 с), так что рычаг надо перепроверять на layout-победителе.
- `hdfsBytesRead` пуст во всех 2695 записях, `scanRatio` в агрегатах пуст. Утверждать, что min/max или bloom реально отсекают страйпы, по этому архиву нельзя. В JSON нет `rowsRead`, `filesOpened`, `partitionsSelected`, `cpuMs`, shuffle и spill.

На M/L и на финальное сравнение Spark/Hive/LLAP этот прогон не распространяется. `final_comparison.tsv` только назначает пять движковых профилей на плоский layout; замеров Hive в архиве нет.

Оговорки к выбору:

1. Победитель — перезаписанная таблица **без** колонок партиции. Соседние плоские базы (`MINMAX_SORT sorting=[]`, `BLOOM_USER bloom_columns=[]`) отстают на 20–60 мс среднего p50, то есть на единицы процентов. Это шум материализации, не эффект фактора.

3. Метка `tieBreakClass=partitioned` для пустого списка колонок — артефакт классификатора (id содержит `PARTITION`). Тай-брейк победителя не выбирал: 1111 мс заметно меньше 1125 мс.

## Факторы

Дельты p50 относительно пустого варианта того же эксперимента. Для сортировки и bloom пустой вариант — честный контроль на той же схеме перезаписи.

### Партиционирование

Плоский вариант — лучший p50 почти на каждом общем запросе. Дата помогает только там, где предикат попадает в ключ партиции.

Часовая нарезка на scale S для этого набора запросов нежизнеспособна: даже запрос с фильтром по дате (`Q01`) в 6 раз медленнее дневной партиции. Дневную партицию имеет смысл оставлять отдельным layout под `Q01`/`Q06`, а не базой для equality и полной проекции `LOGON`.

## Что архив не позволяет утверждать

- Долю прочитанных байт и реальность stripe/row-group skip: `hdfsBytesRead` всегда `null`, хотя поле в контракте метрик обязательное. `enginePlan` в успешных measured-записях есть (текст logical plan), в агрегаты не свёрнут; физического плана с числом файлов и байт в JSON нет.
- Поведение при concurrency 5 и выше.
- Hive Tez и LLAP, в том числе холодный/тёплый кэш. Пять строк `final_comparison.tsv` — назначение профилей на layout победителя, не результаты.
- Перенос на 500 ГиБ и 1024 ГиБ. Часовые партиции и bloom, бесполезные на 23 ГиБ ORC, на L могут повести себя иначе, но масштаб провала date+hour (десятки секунд на запросе без partition predicate) с ростом числа партиций станет только хуже.
- Причину, почему сырая база на `Q07_NARROW` медленнее перезаписи с пустыми факторами на ~0.5 с.

## Что брать в следующий прогон

1. Базовый layout для equality и агрегатов — плоская перезапись без bloom и без партиций. Отдельный layout с партицией только `event_date` — для `Q01_PARTITIONED` и `Q06_PARTITIONED`. `event_hour` на S не материализовать.
2. Bloom `userLogin`/`session` на S выключить. Сортировку не объявлять победителем; если оставлять один вариант для проверки min/max, то `[__time,userLogin]`, и только вместе с ненулевым `hdfsBytesRead`.
3. Vectorized reader оставить `true`. Pushdown перепроверить на плоском layout-победителе, не на сырой базе.
4. Починить сбор `hdfsBytesRead` (и по возможности `filesOpened`, `rowsRead`) до прогона M. Без этого факторы skip не отличить от шума драйвера.
5. `Q07_NARROW` в текущем виде — тест выгрузки 53.7 млн строк, а не тест ORC. Для SLA 3 с нужен либо лимит/агрегат, либо отдельный порог на этот запрос. `Q07_WIDE` оставить контролем column pruning, не целью SLA.
6. Не ставить `Q01_PARTITIONED` и `Q06_PARTITIONED` на вариант с пустым `partition_columns`.
7. Конкурентность 5 и движки из `final_comparison.tsv` запускать после пункта 4, на одном плоском layout плюс дневной партиции, а не на всей матрице факторов.
